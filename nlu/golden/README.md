# nlu/golden — 태깅 품질 golden set

> Push-Point v2.1 — 마지막 업데이트: 2026-07-26

`just eval`이 읽는 태깅 정확도 측정용 데이터셋. JSONL 형식으로 커밋한다.

## 스키마 (한 라인 = 한 링크)

```json
{"url": "...", "snapshot": {"title": "...", "description": "...", "body_text": "...", "keywords": "..."}, "expected_tags": ["...", "..."]}
```

- eval은 **네트워크 접근 0** — 태거 입력은 snapshot 필드만 사용한다. URL을 다시 fetch하지 않으므로 결과가 시점에 무관하게 재현된다.
- snapshot은 **런타임 태거 입력과 정확히 같은 표면**이다(`title`·`description`·`body_text`·`keywords`, 도메인은 `url`에서 파생). 이게 train/serve skew를 없앤다 — 그래서 golden은 **프로덕션 스크랩 경로**(`pushpoint golden-capture`, go-trafilatura 본문 추출)로 캡처한다. 더 풍부한 소스에서 뜨지 않는다.
- `keywords`(발행자 분류)는 **2026-07-26에 추가했다.** 원래는 "현대 웹에서 대체로 죽은 신호"라 보고 제외했는데, 실측해 보니 dev 62건 중 18건, test 61건 중 23건에 실제로 있었다. 다만 스키마에 넣은 근거는 존재율이 아니라 **측정된 기여**다(아래).
  - 본문이 **있을 때**는 Recall@3 기여가 0이다(dev·test 모두 +0.000) — 분류가 말하는 것을 본문이 이미 말하고 있다.
  - 본문이 **없을 때** 비로소 값을 한다: dev +0.065, test +0.049. 그리고 본문이 없는 상황이 바로 이 필드가 필요한 상황이다 — 스크랩 실패·SPA·봇 차단, 즉 클라이언트 캡처 경로.
  - 그래서 eval은 이 둘을 **따로** 낸다. 하나만 재면 "쓸모없다"와 "필수다" 중 아무 쪽으로나 읽힌다.
  - golden은 개발자 문서가 많아 분류 보유율이 30% 안팎이지만, 실사용에서 자주 저장되는 한국어 뉴스는 거의 항상 `article:section`을 낸다. **즉 이 측정치는 실사용 이득의 하한이다.**
- `expected_tags`는 태그 사전(`nlu/dictionary/`)에 존재하는 name만 사용한다.

## 분할: dev 62 / test 61 / wild 31

- **dev.jsonl (62건)**: 규칙·threshold·사전 튜닝은 여기에만 대고 한다.
- **test.jsonl (61건)**: 동결. 게이트 판정(마일스톤 진입/종료 조건)은 동결된 test로만 한다.
- **wild.jsonl (31건)**: 개발 블로그 밖의 실제 웹(소셜·커머스·앱스토어·커뮤니티). dev와 같은
  등급이고 게이트가 아니다. **dev/test와 합치지 않고 따로 낸다** — 합치면 이 세트가 드러내려는
  격차가 평균 뒤로 사라진다. 배경은 아래 「wild.jsonl」 절.

## 동결 규칙

- 태거를 golden set에 맞추는 것은 허용, **golden set을 태거 출력에 맞추는 역방향은 금지**.
- test.jsonl 수정의 유일한 예외는 라벨 오류(잘못 부여된 expected_tags) 수정이며, 수정 사유를 커밋 메시지에 남긴다.
- **wild.jsonl은 dev와 같은 등급이다** — 들여다보며 고쳐도 된다. 게이트 판정에는 쓰지 않는다(아래 참조).

## 지표 정의 (`just eval` 출력)

- **hit**: 예측 top-3 ∩ expected_tags ≥ 1
- **Recall@3**: hit 수 / 전체 건수
- **세 변형을 동시 측정**: `full`(도메인+제목+설명+본문) / `no-body`(본문 제외 — 본문 기여 Δ) / `baseline`(도메인 휴리스틱만 — 규칙 기여 Δ).
- 태그별 precision/recall(full, top-3 기준)과 태그별 golden 등장 빈도를 표로 함께 출력한다.

## 세트 확장 (2026-07-25)

최초 100건에는 **네이버 블로그·티스토리·dev.to가 한 건도 없었다** — 이 앱의 사용자가 실제로
가장 많이 저장하는 플랫폼이 빠져 있으면 그쪽 스크래퍼 회귀를 영원히 못 잡는다. 23건을 추가해
123건이 됐고(네이버 8·티스토리 7·dev.to 2·Hashnode·GitHub Pages·개인 도메인·LINE·당근),
**23건 모두 본문 확보에 성공**했다. `expected_tags`는 태거 출력과 무관하게 콘텐츠를 보고
라벨했고 추가분으로 어떤 튜닝도 하지 않았으므로 동결 규칙(태거를 golden에 맞추는 것은 허용,
golden을 태거에 맞추는 것은 금지)에 어긋나지 않는다.

## wild.jsonl — 실제 웹 세트 (2026-07-26, 31건)

**dev·test 123건은 전부 개발 블로그다.** 소셜/영상이 dev에 0건, test에 1건(1.6%)이다. 그런데
사용자가 실제로 저장하는 건 X·유튜브·인스타그램이다. **`test 0.885`는 사용자가 쓰지 않는
분포에서 잰 숫자였다.**

이 공백은 세트를 만든 방식에서 나왔다. 큐레이션이 "사전 30태그를 고루 덮는 대표 URL"을 기준으로
삼았고, 그 기준을 가장 잘 만족하는 것이 개발 블로그다. 한 축이 빠진 게 아니라 **선택 기준이
한 종류의 웹만 통과시켰다.**

wild는 32개 도메인을 직접 넣어 보고 만들었다(1건은 404로 탈락). 커머스·앱스토어·채용·레시피·
위키·게임·강의·지도·음원·커뮤니티 등, 저장은 하는데 golden에 없던 곳들이다.

| 세트 | Recall@3 full | no-body | baseline | 한국어 | 영어 |
|---|---|---|---|---|---|
| dev (62)  | 0.952 | 0.871 | 0.355 | 1.000 | 0.912 |
| test (61) | 0.885 | 0.820 | 0.344 | 0.941 | 0.815 |
| **wild (31)** | **0.710** | 0.516 | 0.290 | 0.692 | 0.722 |

**-17.5pp(test 대비).** 그리고 미스 9건이 **전부 "정답 0점"** 이다 — 순위를 아무리 다시 매겨도
0.710이 상한이라는 뜻이고, 신호가 밀린 게 아니라 아예 없거나 틀렸다는 뜻이다.

### 0.710에서 태거 몫과 캡처 몫을 갈라야 한다

**0.710은 태거 품질이 아니다.** 31건 중 4건은 스냅샷의 신호(제목+설명+본문)가 200자에 못 미친다 —
스크래퍼가 페이지가 아니라 **벽을 물어온 것**이다(imdb의 `JavaScript is disabled` 166자,
Reddit의 인증 대기 37자 등). 그 항목들은 태거를 어떻게 고쳐도 영원히 miss다. 해법은 태거가
아니라 클라이언트 캡처다.

```
신호 200자 미만 4건(맞힌 것 1) — 캡처가 벽·빈 응답을 물어온 몫이라 태거로 못 고친다.
  나머지 27건 기준 Recall@3=0.778 — 태거를 고쳐서 올릴 수 있는 상한이다.
```

그래서 읽는 법은 이렇다: **태거를 고쳐서 갈 수 있는 데까지가 0.778이고, 0.710과의 차이는
스크래퍼·클라이언트 캡처가 가져가야 할 몫이다.** 두 수를 같이 내지 않으면 캡처 결함이
태거 품질로 잘못 귀속된다 — 이 PR의 첫 판에서 실제로 그렇게 썼다가 리뷰에서 잡혔다.

임계값 200자는 **근사치이고 그렇게만 쓴다.** 200자가 넘는 벽도 있고(threads 로그인 페이지가
219자다) 200자 미만의 진짜 짧은 글도 있다. 벽인지를 내용으로 판정하려 들지 않는 이유는,
봇 차단 페이지에도 그럴듯한 제목이 있어서(`Reddit - Please wait for verification`)
그런 규칙 자체가 틀릴 수 있는 추론이 되기 때문이다. 세는 것은 글자 수 하나다.

### 여기서만 보이는 결함 8종

개발 블로그 코퍼스에서는 원리상 안 나오는 것들이다. 태그별 표에서 `golden=0`인데 예측된
태그(`javascript`·`sports`·`realestate`·`book`)가 곧 오탐의 지문이다.

| | 증상 | 증거 |
|---|---|---|
| A | **봇 차단 페이지가 본문이 됨** | imdb·dribbble 본문이 둘 다 정확히 166자 `"JavaScript is disabled…"` → 태그 `javascript` |
| B | **푸터·상용구가 본문이 됨** | 멜론 푸터 주소 `경기도 성남시` → `sports`(별칭 `경기`) · 유튜브 채널설명 `ios(아이폰) 👉 apple.co/…` → `ios` · 노션 `광고 차단기로 인해 동영상이…` → `video` · 레시피 `동영상 조리순서` → `video` |

E가 가장 깊다. 한국어 Recall이 dev 1.000인데 wild 0.692인 이유가 이것으로 설명된다 —

### 이 세트가 게이트가 아닌 이유

**dev와 같은 등급으로 둔다.** 만드는 과정에서 위 8종을 항목 단위로 다 헤집었기 때문에,
이걸로 고친 뒤 이걸로 재면 자기 채점이 된다. 게이트 판정은 계속 동결 test로 한다.

**test를 늘리는 것 자체는 필요하다** — 61건이 개발 블로그뿐이라 대표성이 없다는 게 이 측정의
결론이다. 다만 늘릴 때 넣을 것은 **개별 항목을 들여다보지 않은** 새 배치여야 하고, 그건
8종을 고친 뒤에 뽑는다. 순서를 뒤집으면 "고쳤다"가 측정 불가능해진다.

|---|---|---|---|---|---|
| dev (62)  | 0.952 | 0.806 (+0.145) | 0.355 (+0.597) | **1.000** | 0.912 |
| test (61) | 0.918 | 0.770 (+0.148) | 0.344 (+0.574) | **1.000** | 0.815 |

`just eval-summary` (요약, TextRank vs lead-3 베이스라인):

| 세트 | 커버리지 | desc 중복 | intra 중복 | 태그 보존 | 결정성 | 본문 추출 |
|---|---|---|---|---|---|---|
| dev  | 0.855 (lead 0.919) | **0.125** (lead 0.397) | 0.208 (lead 0.289) | **0.868** (lead 0.830) | 1.000 | 59/62 |
| test | 0.885 (lead 0.951) | **0.102** (lead 0.342) | 0.244 (lead 0.254) | 0.815 (lead 0.815) | 1.000 | 60/61 |

**④ 태그 보존의 분모는 두 시스템이 모두 요약을 낸 항목**이다. 전체 건수로 나누면 가드가 없는
lead-3의 커버리지가 구조적으로 높아, 가드를 가진 쪽이 가드 때문에 손해를 본다(그건 ①이 재는
축이다). 분모를 바로잡자 TextRank가 dev에서 앞선다(0.868 vs 0.830).

성능: `BenchmarkSummarize` 32KB 본문 기준 **1.5ms/문서**(645KB alloc) — 비동기 tag 잡에서 돌므로 저장 p99 게이트와 무관하다.

**이전 측정(2026-07-25 오전, 본문 추출 버그 상태)**: 태깅 dev 0.900 / test 0.880, 요약 커버리지 dev 0.740 / test 0.660, 본문 추출 78/100. 한국 기술블로그(카카오뱅크·토스·브런치·velog 등)가 `transform: short internal buffer`로 본문 0B였고, goquery가 이미 파싱한 DOM을 trafilatura에 넘기도록 고쳐 **본문 확보 78→96건**, 한국어 태깅 Recall@3 0.895→**1.000**, 한국어 요약 커버리지 0.44~0.58→**0.90~0.92**가 됐다. 이 버그는 어떤 테스트도 실패시키지 않았고 **스팟체크로 내용을 직접 읽다가** 발견됐다 — `본문 추출` 지표를 eval에 넣은 이유다.

- **규칙 태거가 도메인 베이스라인을 +52pp 상회.** 다만 그 마진은 부풀려진 표기다 — 내용을 안 보는 상수 예측기 `{article, tutorial, dev}`가 이미 test 0.721이고, Phase A의 대응표본 실제 우위는 **+16.4pp**(McNemar p=0.0063)다. M5 진입 게이트는 그 기준으로 재정의됐다(02-TECH-SPEC.md).
- **본문(body_text)이 Recall@3를 +12~14pp 올린다** — 본문 추출의 실측 이득.
- 튜닝 여지(dev 관찰, 후속): `data`(alias `데이터`가 한국어 텍스트에 과다 매칭)·`backend` 정밀도 낮음, 저빈도 태그 미탐. 사전 alias 정제는 새 마이그레이션이 필요해 별도 작업.
- 남은 본문 미확보 4건은 **medium.com(SPA + 봇 차단)** 계열이다 — 어떤 순수 Go 경로로도 못 잡는다. 해법은 헤드리스가 아니라 **클라이언트 캡처**(사용자의 로그인된 브라우저가 본문을 함께 보내는 북마클릿·Share Extension)이고, 로드맵 항목이다. 로그인 벽·유료 구독 아티클도 같은 경로로 풀린다.

## 베이스라인과 상대 게이트

- eval은 항상 "도메인 휴리스틱만" 베이스라인 구성을 동시 측정한다.
- 게이트는 상대 조건이다: M5 진입 = Phase A가 상수 예측기 대비 대응표본 유의(McNemar p<0.05), M5 종료 = 앙상블이 Phase A 대비 회귀 0 + 개선 5건 이상. **1항목 = 1.64pp**이고 우연과 구분되는 최소 개선이 5항목이라, 게이트를 백분율이 아니라 항목 수로 쓴다.

## 수집 방법 — `pushpoint golden-capture`

- 입력 TSV(한 줄 `url<TAB>tag,tag,tag`)를 **프로덕션 스크랩 경로**로 돌려 snapshot을 채운 JSONL을 낸다:
  `go run ./cmd/pushpoint golden-capture urls.tsv > out.jsonl`. 이게 golden==runtime을 강제한다.
- URL·`expected_tags`는 사전 30태그를 고루 덮는 실제·대표 URL을 큐레이션하고(한국어 40 / 영어 60),
  `expected_tags`는 태거 출력이 아니라 **콘텐츠에 실제로 맞는 사전 태그**를 독립적으로 라벨한다(동결 규칙).
- 도메인·content_type 비율을 유지하는 층화 샘플링.
- **대표성은 "사전 태그를 고루 덮는가"로 판정하지 않는다.** dev·test가 그 기준으로 만들어졌고
  결과는 개발 블로그 123건이었다(wild 절 참조). 도메인 종류 — 소셜·커머스·앱스토어·커뮤니티가
  들어 있는지 — 를 함께 본다.
- **URL은 실재해야 한다.** wild 초안에서 `airbnb.com/rooms/1234567` 같은 가짜 ID를 썼는데,
  차단 사이트는 404든 403이든 똑같이 빈 스냅샷을 내서 **가짜인 줄 몰랐다.** 차단 도메인일수록
  실재 확인이 필요하다.

## 유니코드 정규화 (2026-07-26)

`Normalize()`가 NFC 합성을 먼저 한다. 없을 때와의 차이:

| 입력 | dev | test |
|---|---|---|
| NFC (평소) | 0.952 | 0.885 |
| **NFD (정규화 없음)** | **0.710** | **0.689** |
| NFD (정규화 있음) | 0.952 | 0.885 |

한글은 "한"을 U+D55C 한 글자로도, `ᄒ+ᅡ+ᆫ` 세 코드포인트로도 쓴다. 눈에는 똑같고 바이트는
다르다. 정규화가 없으면 **한국어 태깅의 3분의 1이 사라지는데 오류도 로그도 없다** — 그날
저장한 것만 태그가 없는 채로 남는다. macOS 파일명이 NFD이고 일부 웹 폼·클립보드·iOS 공유
경로가 그대로 넘긴다.

`Normalize()`에 둔 이유는 그것이 **사전 매칭과 `corpus_df` 누적이 둘 다 지나는** 유일한
관문이기 때문이다. 한쪽만 정규화하면 누적 키와 조회 키가 갈라져 df가 조용히 0에 머문다.

## 지표가 못 보던 두 가지 (2026-07-26, `just eval`에 추가)

`just eval`이 Recall@3 하나만 내던 동안 구조적으로 안 보이던 것들이다.

| | dev | test |
|---|---|---|
| **경계 동점** (3위·4위 점수가 같아 태그 이름 알파벳순으로 갈림) | 30/62 = 48% | 22/61 = 36% |
| 미스 — **정답 태그 0점** | 3 | 6 |
| 미스 — 순위 밀림 | 0 | 1 |
| **재랭킹 상한** | 0.952 **(+0.000)** | 0.902 (+0.016) |

**경계 동점**은 hit@3가 원리상 못 본다 — 3위 안에만 있으면 통과이기 때문이다. 그런데 가중치를
건드리면 이 덩어리가 통째로 재배열되면서 Recall@3는 거의 안 움직인다. E1(사전 확장이 동결
test를 1.7pp 떨어뜨린 것)이 사흘간 안 보인 이유가 여기 있다.

**미스 해부**는 어떤 개선이 유효한지를 가른다. 0점 미스는 순위를 아무리 바꿔도 못 고치고
태그를 threshold 위로 **승격**시켜야 하는데, 그건 오탐 대량 유입이라는 다른 위험이다.
**dev는 미스 3건이 전부 0점이라 재랭킹으로 얻을 것이 0.000이다** — 재랭킹 계열 개선은
dev에서 아무 신호도 못 만든다.

## B1 게이트 측정 (2026-07-26)

[12-BACKLOG.md](../../docs/v2/12-BACKLOG.md) B1(요약을 FTS 색인에)의 착수 조건은 **"요약에만
있고 title·description·tags에는 없는 3-gram을 하나 이상 얻는 링크 비율 30% 이상"**이었다.

| 항목 | 값 |
|---|---|
| 대상 | golden 123건 (dev 62 + test 61) |
| 요약 없음 | 16건 |
| **요약에만 있는 3-gram을 얻는 링크** | **107건 = 87.0%** |
| 게이트 30% | **통과** |

3-gram으로 센 이유는 FTS5 trigram 토크나이저가 그 단위로 색인하기 때문이다 — 새 검색 표면의
크기는 실제 검색이 쓰는 단위로 재야 의미가 있다. 87%는 요약이 제목·설명이 담지 못한 어휘를
**대부분의 링크에서** 실제로 들여온다는 뜻이고, B1은 착수 근거를 얻었다.

## 필드 추가 — `pushpoint golden-refill`

태거가 새 필드를 쓰기 시작하면 그 필드가 없는 golden으로는 **개선을 측정할 수 없다**(Δ가 항상 0).
그렇다고 `golden-capture`로 전체를 다시 뜨면 그 사이 바뀐 페이지 때문에 `title`·`body_text`까지
흔들려 **이전 측정치와의 비교가 끊긴다** — test는 동결 세트라 특히 안 된다.

`golden-refill`은 재fetch하되 **비어 있는 필드만** 채운다. 이미 값이 있는 필드는 건드리지 않는다:

```
go run ./cmd/pushpoint golden-refill nlu/golden/dev.jsonl > /tmp/dev.jsonl
```

- fetch에 실패한 항목은 원본 그대로 통과시킨다 — URL이 죽었다고 항목을 잃으면 세트가 조용히 줄어 지표 비교가 불가능해진다.
- 2026-07-26 `keywords` 추가 시 실제로 이 도구로 채웠고, **다른 필드가 하나도 바뀌지 않았음을 확인한 뒤** 커밋했다(dev 18/62, test 23/61 채움, fetch 실패 0).
