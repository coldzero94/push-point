### Group A — build the missing yardsticks first

No declaring done without measurement is this project's rule, and yet **two of the yardsticks do not exist.** The one that judges success (consecutive days of use) and the one that measures search quality and latency.

#### A1. `scripts/streak.sh` — the consecutive-save-day judge  ✅ done 2026-07-26 (`just streak`)

- **What it solves**: the M6 completion bar is "4 weeks of consecutive daily use" and there is nothing that judges it. `scripts/streak.sh` is nailed into three places — the 08 §2 table, the Week 4 item, and the milestone verification command table — as "count > 0 for 28 consecutive days", and the file does not exist (checked 2026-07-26: there is no `streak.sh` under `scripts/` — the reason for not enumerating what is there is that this parenthesis goes stale every time the list grows).
- **How it works**: read `by_day` from `GET /api/v1/stats`, judge whether the last 28 days were saved on consecutively, exit 0/1. Exposed as `just streak`. 30 to 40-odd lines of shell + jq. It is not CI — it is a judge a person runs at the end of M6. The output stops at one verdict line plus one evidence line (about the level of `streak 12일 / 활동 23일 / 28일 목표 미달 (exit 1)`). No bars, no colour.
  - **The definition of consecutive is nailed down in one place and matched to iOS.** The rule `ios/PushPoint/StatsView.swift` already settled — "if today has no save yet, count from yesterday" — is used verbatim in the shell. If it reads as zero just after midnight, nobody believes the number.
  - `by_day` is a GROUP BY result, so **a day with no saves has no row at all.** Filling in the missing dates with zero before counting is the only non-obvious logic in this script. Leave those two lines in the script's comments as the definition and have the 08 §4 table point at them.
- **Does it work with the data we already have**: yes. `GET /api/v1/stats` is implemented and `by_day` is a 30-day window in server localtime. New contract 0, schema 0, dependencies 0.
- **Size**: S
- **Risk**: low. The only real risk is **putting this number on a screen**. The product's success metric is that number, so the moment the streak is displayed large there is an incentive for self-deception — save one meaningless link to keep the streak alive. Make the thing you measure the goal and the measurement dies. **That sentence was retired on 2026-07-29** — the shipped behaviour was already the opposite (`scripts/streak.sh:27-30` recorded it first), and a rejection note that no longer matches the code protects nothing while still misleading whoever reads it. The streak is visible on both clients, and the price accepted for that is knowing the Goodhart pressure is on. The agreed exposure is **the streak plus one goal line, and no further**; growing it into badges, levels or notifications is a separate decision (14 §D7).

### Group B — how far search reaches

Right now `links_fts` looks at four columns only: title · description · note · tags. description is promo copy the publisher wrote and note is mostly empty, so **the real searchable text per link is effectively one line of title**. Meanwhile `body_text` (up to 32KB per link) and the 2 to 3-sentence `summary` are already in the DB, and only the tagger and the summarizer read them.

This group proceeds **in B1 → B2 order and no other.** Undoing B1 is one reindex; B2 is a new table plus a full backfill. Buy the cheap side first, confirm it was worth something, then buy the expensive one.

#### B1. Put the summary on the existing index (no schema change)  ✅ done 2026-07-26 — gate passed at 87%

- **What it solves**: a word that was not in the title or the description cannot find what you saved. `summary` measured a desc-overlap of 0.102~0.125 (lead-3 baseline 0.34~0.40) — meaning MMR picked sentences that do not overlap the description, and that is the only measured evidence that a new search surface really exists.
- **How it works**: no migration is written. Make `reindexFTS` (`backend/internal/store/sqlite.go:206`) put `description || ' ' || summary` into the FTS `description` slot. **The columns of `links_fts` are under no obligation to match the columns of `links`** — `searchFTS` uses them only for MATCH and bm25, every displayed value comes from `links`, and thanks to the decision not to build snippets the indexed text never reaches a screen. Then promote `SetSummary` (`backend/internal/store/sqlite_tagger.go:81`, which right now even carries a comment saying "links_fts is not touched") to the same contract as `SetRuleTags`, so that it calls `reindexFTS` inside the same write transaction. Existing links get a one-time backfill.
  - The result: zero lines of schema, zero lines of contract, **0 new bm25 column weights** (a tuning knob with no measurement set to justify it is simply not bought), and the undo is one reindex.
- **Does it work with the data we already have**: yes. `links.summary` (migration 0005) is already populated and is currently read in exactly one place, `LinkDetail`. That migration explicitly deferred it — "not put into links_fts either (revisit at stage 2)" — and the revisit trigger 08-DEVELOPMENT-PLAN.md wrote down (summary coverage above 85%) has already fired at a measured 0.855 (dev) / 0.885 (test).
- **Size**: S
- **Risk**: the gain may be small. `maxSummaryRunes = 450` (`backend/internal/summarizer/summarize.go:26`), so only part of the vocabulary in a 32KB body comes back. And 0.855-coverage, turned over, means **14% have no summary at all**, and the links that trip the guard (`MinBodyRunes = 200`) are exactly the ones with a thin description — the ones that need the help most. On top of that, longer indexed text can move existing rankings slightly through bm25 length normalization — and that **has not been measured.**
- **Entry condition (the gate)**: produce one number before any code. Using the 123-item `nlu/golden`, count **"the share of links that gain at least one 3-gram that exists only in the summary and not in title·description·note·tags"** and record it in `nlu/golden/README.md`. It comes out in an hour from data already on disk, and it puts a number on the size of the new search surface for the first time. **Under 30% and it folds.** — **measured 2026-07-31: 81.5% (154/189). Pass.**
  It reproduces with `just b1-gate` and the full text is in `nlu/golden/README.md`. But **the count gained and the count of
  summaries are identical** (154=154) — structurally so, because the summary comes out of `body_text`, which is not indexed.
  Which means the gate reduces to "does a summary come out at all", and the discriminating power sits on the 18.5% side
  where `Summarize` returns an empty string. It still answered what was asked ("is there a new search surface").
- **Verification**: re-measure `just bench-search` (A2), compare index file size before and after, keep `scripts/coldstart.sh` < 1s.
- **Retirement condition**: a dedicated `summary` column and per-column weights get formalized as `0010_` only after a few weeks in this shape have actually piled up cases of "I found it thanks to the summary". If the cases do not pile up, it does not get formalized.

#### B2. The head of the body as a separate index — 2-tier search

- **What it solves**: what you remember is a phrase inside the body, and the body is not in the index. What B1 buys back is 450-runes and no more.
- **How it works**: rankings are **not blended — they are appended.**
  1. `links_fts` is not touched. No DROP+CREATE, no added column. The existing index · existing bm25 · existing cursor semantics all survive intact.
  2. Exactly one new table: `links_text_fts(summary, body_head, tokenize='trigram')`, rowid = `links.id`. `body_head` is the first **2KB** of `body_text` (cut on a rune boundary). Syncing is one added INSERT line in the same transaction as `reindexFTS`.
  3. Search is 2-tier. Tier-1 = today's `links_fts` results, ranking and order 100% identical to today. Tier-2 = links that matched only `links_text_fts`, appended **after tier-1 is fully exhausted.** The cursor carries the tier number (the cursor is an opaque string, so no contract change).
  4. **No bm25 weight tuning.** The point is to not make a judgment there is no evidence to justify. There is structurally no path by which existing results get worse, so the regression risk is zero and the golden set only has to measure "how much better".
- **Why the columns are not mixed**: even given column weights, FTS5 bm25 does its length normalization (k1·b fixed, not tunable) over **the token count of the whole row**. trigram runs at about 1 token per character, so a mere 2KB-slice of body jumps a row's token count from dozens to thousands. Then a link that has a body loses to a link that does not even on an exact title match. It is a structural inversion that "adjust it with weights" cannot stop.
- **Does it work with the data we already have**: yes. `links.body_text` (migration 0004) is populated (not one of the 123 golden items is empty, and 119 of them are over 200-runes (dev 59/62 · test 60/61)). The API contract does not change — the parameters of `GET /api/v1/search` and the code in `SearchScreen` both stay as they are, only the results grow.
- **Size**: M (assuming the A2 harness exists first)
- **Risk**: trigram index size is directly proportional to text length. It runs head-on into the search p99 < 30ms gate, so **it must be measured before it is switched on.** The full backfill at migration time blows well past cold start once (one-time, but the number gets recorded, not hidden).
- **Entry condition**: A2 done + the B1 gate passed + a few weeks of real use of B1.
- **Fallback line**: if p99 does not hold, shrink `body_head` from 1KB → 512B, and if that still fails, fall back to the reduced version that indexes `summary` only (= where B1 already got to, the zero-risk floor).
- **What it does not do (kept as is)**: no snippets or highlights (11 §10-4), no "title only / include body" toggle (for a single user, a choice is a tax), no API exposure of `body_text`.

### Group C — the friction of re-finding

#### C1. An open signal — one `links.opened_at`  ✅ done 2026-07-26

- **What it solves**: saving is easy, it is one tap — but after saving, **the app has no idea which links actually got opened again.** That fact is nowhere in the schema (checked 2026-07-26: `opened_at` and `open_count` appear zero times across backend, frontend, ios and extension). Of the five stages of the core loop, save, scrape and tagging are all instrumented; only the last stage, re-opening, sits at zero.
- **Why it only holds here**: the better the tagger runs (test Recall@3 0.885), the more old-but-relevant links the tag filter pulls up, and the more often "have I already seen this?" comes up. **It is friction that grows as the differentiator works better**, which makes it a different animal from read/unread in a general bookmark app.
- **How it works**: one column, one endpoint, one chip.
  - Migration `0010_link_opened_at`: `ALTER TABLE links ADD COLUMN opened_at INTEGER`, exactly that and nothing else. No `open_count`, `updated_at` unchanged (touch it and list ordering and the inspector's meta both wobble).
  - Contract: `POST /api/v1/links/{id}/open` → 204. It has the same sub-action shape as `POST /api/v1/links/{id}/retry`, so it is not a new pattern. The server runs a single statement, `UPDATE links SET opened_at = ? WHERE id = ? AND deleted_at IS NULL` — outside the save path, so it has nothing to do with the save p99 gate. The client is fire-and-forget; a failure is lost (no retry queue).
  - The response gains `LinkDetail.opened_at` only; the list item `Link` does not get it. The card has nowhere to show it anyway (status is a 2px rail and nothing else), so there is no reason to grow the list payload.
  - One `unopened=true` on `GET /api/v1/links`. Not a two-way boolean — nobody uses a "things I re-read" filter. A partial index `... ON links(created_at DESC, id DESC) WHERE deleted_at IS NULL AND opened_at IS NULL`, and the keyset cursor rides it unchanged.
  - Only two places on screen. One "not opened" chip in the filter row (the same component as the existing status chips), and one "last opened" line in the inspector meta. No card badge, no dimming.
  - The call sites are seven — web `LinkCard` · `useRowKeyboard` · `LinkInspector`, iOS `ContentView` · `LinkDetailView` and so on — and they collapse into one helper. The iOS embedded mode rides the same contract too, since `ppcore` brings up an in-process HTTP server — **no added gomobile bind surface.**
- **Does it work with the data we already have**: no. It is the only candidate in this group that needs a new column. It does not need a new table, at least.
- **Size**: S~M (the column is S; regenerating for the contract's three consumers is the whole cost)
- **Risk**: this signal counts **only opens that went through Push-Point.** Opening from browser history or straight in the original app registers as zero. So used as a ratio or a metric it structurally reads lower than reality, and believing that number and concluding "I do not read what I save" is a wrong conclusion. Worse, saving less in order to make the ratio look better shaves the success metric itself ("do I use this every day").
- **So here is what gets cut explicitly**: `open_count`, `Stats.opened_this_week`, ratio displays like "saved 12 / opened 3", and any link to A1. **This is not a metric, it is a per-link fact.** Used only as a per-link fact, the undercount is noise on the order of "a few already-read items mixed into the not-opened filter", and the incentive to distort behaviour disappears. Turn it into a metric and every risk above comes straight back.
- **Entry condition**: **bundle it into the same PR** as some other work that touches the contract. Running the three generators on their own for the sake of one column is this candidate's only real cost, and bundling makes it vanish.
- **Retirement condition**: if after 4 weeks the "not opened" chip has never once been tapped, remove the `unopened` parameter and the chip (the column stays — migrations are append-only). Write it into the PR description and actually check it at the M6 retrospective.
- **Unresolved**: serving the `unopened` list as `created_at DESC` still leaves old unopened links buried at the bottom. An `order=oldest` parameter may be the answer, and that is also the point the "reviving buried links" and "read state" entries in section four each arrived at. **Not deciding now** — use the chip first, and if scrolling down actually becomes annoying, put it on as one parameter then.

### Group D — writing back from the sheet

#### D1. An `inbox` tab — taking commands from the sheet

- **What it solves**: when reading the sheet turns into "I should fix this link's note", today that means moving to the web or the app. The sheet is where the skimming happens, and the means to fix things is not there.
- **Why the grid is not made editable**: six designs that treat the `links` grid as an editing surface were reviewed and four were cut, and the signature was the same every time. **There is no way to know which cell a human touched** — Sheets gives neither a row/cell edit timestamp nor a revision id, and Drive's `modifiedTime` is per file and gets bumped by our own sync, so it cannot be told apart from a human edit. On the other side `links.updated_at` is bumped by scraping, thumbnails and summarizing alike, so it is no approximation of a human edit time either. Which means that instead of the design preventing one stray sort or a paste one column off, it **executes them faithfully.** The controlled dictionary is no defence line either — every tag name in the sheet came from that dictionary by definition, so no matter how the tag cells get scrambled, `ErrUnknownTag` never fires once.
- **How it works**: separately from the `links` grid, which we **never read**, there is an `inbox` tab that a human writes in. The header is `id | 작업 | 값 | 확인 URL | 실행`. The actions are `메모` · `태그` · `저장` · `삭제` · `재시도`, five of them, each mapping to an API that already exists (`PATCH` · `POST` · `DELETE` · `retry`).
  - **The key is that the `실행` checkbox is the last column.** A human fills left to right, so the check naturally becomes the last action, and "is this row complete" turns from a guess into **a human declaration**. That one cell removes the entire class of "cron fired while I was still typing" accidents.
  - **Nothing is written back into the inbox.** Reading goes by column name and results are written into a separate `inbox-log` tab. Read and then write back by coordinate, and inserting a single column makes the result writer overwrite human input — and Sheets has no range CAS, so no safe variant of that exists.
  - The ledger lives in `data/sheets-inbox.json` as **a hash of the command's content** (not the row number — rows move when you delete and insert). Leave an applied row and it is not applied twice; delete it and it disappears from the ledger too, so the same command can be written again.
  - **No conflict resolution.** A command is imperative intent, not state, so there is no "who is newest" problem. What gets left in `inbox-log` for undo material is the value immediately before the command was applied.
  - **An inbox failure does not block export.** Five of the six designs reviewed took the perfectly healthy forward direction hostage with "stop everything on conflict".
- **Does it work with the data we already have**: yes. Every write goes through the existing HTTP API — no second writing process against single-writer SQLite, and `Normalize`, FTS reindexing, `tag_feedback` and job enqueueing all happen inside the server (the same shape as the `import` subcommand).
- **Size**: M
- **Risk**: it is a tab a human writes in, so the input is arbitrary. Formula cells, error literals, tags not in the dictionary, whitespace in an id and so on all have to be rejected row by row, and it needs a 100-row ceiling that skips the whole batch when exceeded (against paste accidents).
- **Entry condition**: when **five or more** occasions of actually wanting to fix something while reading the sheet have piled up. Before that, the friction of moving to the web or the app is cheaper than this design's complexity.

### Group E — a regression that already happened

#### E1. Pin down the test regression the dictionary expansion caused

- **What it solves**: `fa18e5e` (#30) grew the dictionary from 30 tags into a 42-tag one, and the frozen test Recall@3-score fell 0.902 → **0.885** (measured 2026-07-26 with the variable isolated, `nlu/golden/README.md`). dev sat 0.952-flat, so looking only at dev shows nothing. The cause has been left unexplained.
- **How it works**: add an option to `just eval` that prints "why is this item a miss" in one line — the correct tag's score alongside the scores of the actual top-3. Filter to only the items that newly became misses at 42-tags versus 30-tags, and whether a new tag pushed them out or something else did is immediately visible.
- **Does it work with the data we already have**: yes. eval already holds the scores; it just does not print them.
- **Size**: S
- **Risk**: low. But **the cause may be "the new tag really is more correct and the golden label is written against the old dictionary"** — in which case what needs fixing is the golden, not the tagger, and that runs head-on into the freeze rule ("no reverse-fitting the golden to tagger output"). In that case label review has to be split off as separate work.
- **Entry condition**: none. Better to have it done before the dictionary is touched again — grow it again without knowing the cause and the regressions stack.

**Pinned down (2026-07-26).** The regression is **exactly 1 item** (1 of 61 = 1.6pp, matching the measured 1.7pp difference).

- The item: `blog.naver.com/esteee_/224346723933` — a reading note on George Orwell's 『1984』. Correct answer `book`.
- Before (30-tags) top-3 `article ai book` → after (42-tags) `article culture ai`. The new tag `culture` pushed `book` out.
- The surfaces that fired: `culture` got 「영화」 three times + 「드라마」 twice, `book` got 「독서」 twice. Because the reading note mentions the film and drama adaptations.
- **The golden label is right.** It is not that `culture` is more accurate — the body signal followed **frequency, not precision**.

**And yet the dictionary must not be fixed to match this.** This measurement **came out of the frozen test**, and adjusting the dictionary to fit it is tuning on test — precisely the act the freeze rule forbids (tuning happens on dev only). Changing a controlled vocabulary on the evidence of a single item is overfitting as well.

**What this case points at instead**: the structure where a broad tag wins on frequency in the body is exactly what IDF targets (「영화」 and 「드라마」 are common words). The legitimate follow-up to this regression is not group B but **turning IDF on and measuring it once corpus_df is real**. Until then, **leaving it in a known state** is right — breaking the freeze rule to win back 1.6pp is far more expensive.

### 4.1 Sending things outward

Where this whole class gets stuck: **this product's success metric is "do I use it every day", not "am I good at sending things to other people".** Its identity, too, is "the data does not leave".

- **Weekly / monthly digest (`pushpoint digest`)** — half the problem is already solved. The list is `created_at DESC`, so "what I saved this week" is the first screen of the list, and `GET /api/v1/search` already has `from`/`to`. The real motive is "an artifact to show people", and that is a one-off act of authorship sitting in M6's public-writing slot, not a feature. On top of that, a document where titles and summaries run down the page converges on the shape of the permanently banned reader view. **The piece worth keeping**: if it must be built — markdown to stdout · monthly only · grouped by tag · one line per link · `summary` only for links whose `description` is empty. It starts after the M4 real-device DoD passes, inside M6's public-writing slot. **Nail the retirement condition down first — if I do not run it myself two months running, it gets deleted.**
- **A static public page build (`pushpoint publish`) + a per-link public flag** — 08-DEVELOPMENT-PLAN.md nailed the material for M6's technical write-up to "revising the notes accumulated since M5". What that piece will point at is the bake-off measurements and the numbers in `nlu/golden/README.md`, not a published list of links. The premise "there is nothing to point at" is false. It is also a proposal that quietly lets in a second user (feed.xml assumes subscribers who do not exist), and it is a second surface the design system does not govern — the place where landing-page grammar most naturally comes back. It is an L: contract + migration + three generated outputs + web and iOS toggles. **The piece worth keeping**: showing off the **classifier** rather than showing off links is a different matter — `pushpoint export --tag go --limit 50 --out demo.html`, one row per link with title · domain · attached tags · `confidence` · the evidence signal (domain rule / keywords / body). No schema or contract change, and the dedicated query does not even SELECT `note`, `body_text` or `error`. **Entry condition: after the sentence "this is the thing that came out of it" has actually been written into a draft of the technical piece.** If that sentence never appears, it means this feature is not needed.
- **Exporting the whole archive (`pushpoint export`)** — the central claim is not true. `import.go` is not a DB importer; it is an HTTP client that fires URLs at `POST /api/v1/links`, and `LinkInput` has no tags, created_at, summary or confidence. So building a round-trip test would round-trip the URL only and show green — not a safety net but **false reassurance**. Backup is already solved: the data is one SQLite file, and `cp` or `VACUUM INTO` is more complete than a jsonl round trip (FTS · corpus_df · tag_feedback · job history included).
- **Export plus a one-line backup** — export gets cut for the reason above. Netscape HTML export is the single most typical entry in a bookmark app's feature list and its overlap with the differentiator is zero. **There is one kernel here that cannot be thrown away**: the `rsync` path in 07-DEPLOYMENT.md can produce a torn copy out of a live WAL state, and **nobody verifies that.** **The piece worth keeping**: `pushpoint backup -out backup/ -keep 7` — a consistent snapshot via `VACUUM INTO`, **reopening that copy** to run `PRAGMA integrity_check` plus a link-count comparison, one line of output, old files pruned, exit 1 on failure. The artifact here is not a file, it is **verified restorability**. Scope runs as far as unattended execution under launchd. One test is enough (does the copy hold up against a DB the worker is writing to). The output states explicitly that `thumbs/` is not included.
- **Share text for 1 link** — on the iOS side this is not an improvement, it is a **regression**. `ShareLink(item: url)` takes a `URL` argument, so the receiving app renders a rich link card; swap in a formatted `String` and the card disappears in every receiving app. It trades the preview, the title and the thumbnail away to gain three lines of context. Tags are not a language for recipients either — the 42 controlled terms are a classification axis tuned for my own re-finding, and a summary is a machine sentence that gets misread as my voice. **The piece worth keeping**: the fact that the web has zero outbound affordance at all is a real gap. One "copy" button in `LinkInspector`, format fixed at two lines, `{title}` newline `{url}`. No tags, no summary, no note, no checkbox (note is the only purely human field in the schema, so no room is created for it to leave by the default path by accident). Fifteen lines of code. **Expansion condition: only when there have been five or more occasions within 4 weeks of "pasting it and hand-adding why I saved it" does including note get discussed.**

### 4.2 Aggregate and retrospective screens

Where this whole class gets stuck: **to a single user saving a few links a day, a trend is not information, it is noise.** And a statistics screen is the textbook example of a screen you look at once and never return to.

- **The web rhythm screen (the part that came attached to A1's original proposal)** — **this rejection was overturned on 2026-07-27, and the thing was built and shipped** (11 §8 (3-1), `RhythmSection.tsx`). One ground is still standing — 11 [§9](11-WEB-UX-SPEC.md) wrote this down not as a "screen" but as **a statistics section inside settings**, and into settings it actually went. **Promoting it to a route of its own means answering that ground.** And the one line the rejection note singled out as "the only thing worth putting on the web", `?status=failed`, is **still blank** (13 §2 — the contract has no `Stats.failed_links`).
- **Clipboard text snapshot sharing** — a share button on a single-user self-hosted tool. Wherever it would get pasted is outside this product's loop, and M6's technical write-up is a piece a person writes, not something a clipboard button can stand in for.
- **This month's trajectory — a period retrospective screen** — the headline feature is a structurally empty column. `link_terms` is not a general term ledger, it is **the set of matched dictionary surfaces**, so "the terms that clustered in this period" is the 42 dictionary tags counted under another name = the same column as `by_tag`. `corpus_df`, the comparison baseline, is asleep below `minCorpusDocs` as well. The sketch's "every item links through to a list" only holds once new `domain`, `author` and `content_type` filters are built on `GET /api/v1/links`, and that is a contract change plus three generators. Per-period tag counts are a way of walking back in beside the door 11 §10-2 explicitly closed. **The piece worth keeping**: one array, `by_domain` (top 10, cumulative), on `GET /api/v1/stats`. New endpoints 0, tables 0, migrations 0. The web hangs it under the existing Tags screen (no separate route). **No deltas, no arrows, no colour emphasis — counts only.** **Entry condition: when three or more domains have five or more saves each** — **measured 2026-07-30: zero.**
  The contract was opened for three other fields on the same day, but this one did not meet its condition and **was left out on purpose.** A bundling opportunity came and was not taken, so the next time the condition is met the three generators have to be run for this alone — the cost was known and the delay taken anyway — and one line, `SELECT domain, COUNT(*) FROM links GROUP BY domain HAVING COUNT(*) >= 5`, checks it immediately.
- **Current interests (a recent-20 window)** — the candidate confesses it itself: "it must not claim 'a meaningful change', it has to stop at 'here is what the last 20 look like'". And yet it is named "current interests". At 1 to 3 saves a day, a 3-item threshold on a 20-item window is 15% of the sample, so one day of binge-reading fires it every time. **An instrument that always wobbles is a broken instrument, and in an app whose identity is the dashboard, that is worse than not having one.** It is mechanically excessive too — list items already carry `tags` and `limit` maxes out at 100, so a single `GET /api/v1/links?limit=40` produces both windows. It is also a re-entry through 11 §10-2. **✅ done 2026-07-30** — contract (`Tag.last_saved_at`) and screen (freshness on the tag dictionary row + a "most recently saved" sort) both. No arrows, no deltas, no count-up, exactly as specified. What follows is that spec.
  **The piece worth keeping**: throw the comparison away and keep **freshness** alone. The real pain is "a topic that stopped two months ago sits in the same place as this week's topic", and that is not a complaint about trends but about neglect, and **one date per tag** answers it. One field `last_saved_at` on `Tag` (migrations 0 — a `link_tags` join + `MAX(created_at)`), one "3 days ago" fragment at the end of the tag list row, one "most recently saved" entry in the sort toggle. No arrows, no up/down, no count-up. **"Comparison against the previous window" does not get built until 4 weeks of consecutive real use are behind me and I say I miss it myself.**
- **Cost to open / choosing by time budget** — two candidates collapse in the same place. `duration_sec` and `word_count` are not data that "is there but goes unread", they are **dead columns nobody has ever written** (the plumbing exists; the assignment appears nowhere in production code). So "two query parameters and done, effort S" does not hold. On top of that, counting `word_count` off `body_text` **systematically undercounts the longer the piece is**, because of the 32KB ceiling, and a YouTube `body_text` is the creator's description rather than the captions, so a 40-minute video becomes a "3 minute read" — wrong by the widest margin in precisely the one type where time cost really does change behaviour. Put the filter in without a backfill and **the filter silently hides the entire archive** (the worst failure mode an archive has). An inventory sentence like "47 untouched = 3 hours 12 minutes" is a read-later guilt meter and collides head-on with "no total anywhere" (11 §10-7). **The piece worth keeping**: rewrite it as a defect fix rather than a feature. **Video length only, fact only, one card line only.** Read it only from a source that declares the length as fact (`lengthSeconds` out of the same JSON blob on the YouTube watch page, `og:video:duration`, JSON-LD `duration`). Absent, NULL. `word_count` is not touched. The display is nothing but slipping `42분` into the card's existing mono meta line — with no value, nothing appears. No `max_minutes` parameter, no filter chip, no statistics. **Promotion condition: measure and record the share of videos whose length is known, and discuss a filter only once that number has actually changed a "do I open this now" decision.**

### 4.3 Reviving and state

- **Reviving buried links (a recommendation block)** — **✅ shipped 2026-08-05** (backend, contract and web in #119; iOS in #128). The judgement below is kept as the **evidence as it stood then**. `opened_at` (C1), which was the re-discussion trigger, landed first and turned the "no human has ever touched it" proxy into a real signal, and the "four months" went away when the threshold was lowered to seven days. **What did not change is the unparsed `ADD_DATE` in `import.go`** — every imported link still carries `created_at = now`, so the save-date axis is still a lie and on day eight after an import that whole lump becomes eligible at once. The order written below — "the first task is not UI but the parsing" — was not kept, and that is the debt still outstanding. Original judgement: the period over which it cannot be verified is longer than the feature's own lifetime ("it takes about four months before anything comes out at all"). On top of that, `import.go` parses neither `ADD_DATE` nor `time_usec`, so every imported link carries `created_at = now` — on day 91 the entire imported lump crosses the threshold at once, and this block flips in one step from "permanently empty" to "a bulk dump of an import from three months ago". The key signal (whether it was opened) is missing too, so "no human has ever touched it" is the only proxy, and that cannot tell "not read" apart from "read and there was nothing to fix". **Re-discussion trigger**: after `opened_at` (C1) has actually started recording and three months of that data have piled up. If it gets built then, the first task is not UI but `ADD_DATE` parsing in `import.go` — without preserving the original save date, the archive's time axis is itself a lie.
- **Read state and an "unread" filter** — the proposed mechanism does not solve the proposed problem. The problem is ordering (the only list axis is `created_at DESC`) and the prescription is a boolean, so "everything buried at the bottom" merely becomes "the unread ones buried at the bottom" with a smaller pile. Automatic marking instruments an unobservable fact too — "open original" already sits in five or more places, share, copy and middle-click are not caught at all, and in an app where reader view is permanently banned the server only ever knows "opened" and can never know "read". A false positive makes that link **disappear permanently from the one view that could have rescued it** — a failure mode worse than having no feature. There is nowhere to show the state either (R3: status is a 2px rail, and `done` draws nothing). **What survived out of this is C1** — it does not model "read", it records only the fact "has been opened". It does not use the words read/unread at all.
- **Recovering unreachable links** — half of the problem statement is already implemented. Failure recovery is a finished feature (a status parameter, a failed filter, a dedicated empty-state message, retry buttons on both the card and the inspector). "Unreachable" is not a fact either — `links_fts` indexes title, description, note and tags, so a link with zero tags still turns up in search and in the chronological list as long as it is `done`. The genuinely new part is one thing only, "done links that the tag filter alone cannot catch", and for that one thing the price is a contract change + three generated outputs + a p99 re-measurement. **The piece worth keeping**: not a screen, one number. `just untagged` — the zero-tag share against the total, the count of links that are `done` yet have zero tags, and the url, domain and body_source of the 10 most recent of those. Read-only; contract 0, migration 0, screen 0. **The grounds are this project's own rule**: it claims Recall@3 0.885 on golden while the untagged share of my actual corpus has never once been measured. **Graduation condition: when a zero-tag share above 5% or more than 20 done-but-untagged links is confirmed twice running**, add the filter then — not as a separate parameter but as a reserved sentinel on the existing tag filter, implemented with `NOT EXISTS`, with `just bench-http` numbers from a 100k-row seed attached.

### 4.4 Logs and reports

Where this whole class gets stuck: **this repository already has one ledger nobody reads.** `tag_feedback` is only ever INSERTed in `store/sqlite.go`, and SELECTs outside tests number zero (checked 2026-07-26). Building a second write-only ledger while the first one has no reader is the same mistake again.

- **Searches that found nothing (a zero-hit log table + a screen)** — a good share of the zero-hit cases are not an unknown signal but **a known index coverage hole** (`body_text` was explicitly left out by 0004, `summary` by 0005). Building a table + an endpoint + a screen to rediscover that is the long way round, and the log does not separate the three causes (never saved / mis-tagged / no vocabulary) either. There is no single-instance value: a zero-hit result was already on screen two seconds ago, and the value comes only from accumulation, which needs 30 to 50 searches. **The piece worth keeping**: the version with no table, no endpoint and no screen — two `slog` lines at the end of the search handler (mode and hits on every search, `q` added only when hits is zero). Migration 0, contract 0, client 0, and log rotation is the deletion mechanism. **Run it two weeks, then grep twice.** — **shipped 2026-08-03** (end of Search in `api/handlers.go`).
  Requests carrying a cursor are not counted (that is the second page of the same search, not a new search). How to read it:

  ```sh
  # ① 주당 검색 횟수 — 한 자릿수면 묶음 B 전체의 우선순위가 내려간다
  grep -c '"msg":"search"' <로그>

  # ② 0건 질의 — 본문 문구에 몰리면 답은 화면이 아니라 색인이고 그게 B1이다
  grep '"msg":"search"' <로그> | grep '"hits":0'
  ```
 The first number is the real unknown — **searches per week.** If it comes back a single digit, the priority of the whole search investment (group B included) drops. That is an answer bought with 10 lines. The second: do the zero-hit queries cluster on phrases from the body — if they do, the answer is not a screen but the index, and that is B1. The table and the screen come back out only when the log confirms **10 or more searches per week + the same query returning zero three or more times.** Even then, leave out the "add this word to the dictionary" link — zero hits means "it is not in the archive", not "the vocabulary is missing".
- **A vocabulary gap report** — two of the three branches either already exist or are already empty. Dead vocabulary is a duplicate (the tags screen already shows all 42 dictionary entries in descending `link_count` — a zero-count tag is the last row of that table). Missing vocabulary is something the candidate itself confesses to: "on a balanced corpus whose top surface share is 34~38%, it comes out a nearly empty table". And that branch is the only one of the three that actually costs code (`tagger/match.go` emits matched surfaces only, so you build a second copy of the normalization path and get an empty table for it). Mining new tags out of corpus frequency also pushes "classification, not generation" into resting on a single human gate. **The piece worth keeping**: catch the vocabulary gap **only at the moment I declare it.** (A) one line `slog.Warn("unknown tag", "name", ...)` on the `ErrUnknownTag` branch — the moment I type in a name the dictionary does not have is itself the declaration "I have no word for this subject", and **its precision is 1.0.** (B) at the tail of `just eval` output, at most 3 lines of tags where `removed > added` in `tag_feedback` (silent below 20 total rows). New recipes 0 — the signal arrives in the output of a command that gets run anyway whenever the dictionary is edited.
- **A `tag_feedback` report** — the sketch's core query ("top removed = over-firing, top added = missing aliases") is something `just eval` already produces (a per-tag P/R table on a TP/FP/FN basis). The only difference is the evidence, and the eval side is a fixed 123-item labelled set while the feedback side is a few dozen unlabelled ones — **it redraws the same table on worse evidence.** There is no sample either (measured: 2 rows of tag_feedback in the local DB, all `added`, `removed` 0). And the moment a report implies "fix this rule", the temptation to bypass the golden gate arrives — **if a tool tempts you toward routing around the discipline, it is not the thing to build now.** **The piece worth keeping**: drop the report and turn it into **a golden candidate queue**. `tag_feedback`'s value is not analysis but **hand-labelled ground truth for free** — the final tag set of a link whose tags I corrected is by definition a human-assigned answer. Have `pushpoint feedback-golden` spit out `url<TAB>tag,tag` TSV, which is exactly the format the existing `golden-capture` eats, and "real-world misclassification → dev set → re-measure → fix the dictionary" becomes **the default path**, so the point at which the temptation to bypass appears simply stops existing. Two guards: exclude URLs already in dev/test, and **exclude test.jsonl URLs unconditionally, with no option to override**. **Start point: when `removed` in `tag_feedback` reaches 20 rows.** Before that there are no lines to print.
- **Failure diagnosis + per-domain revival (`pushpoint retry-failed`)** — the premise is wrong. Every card already has a retry button, and so do the failed filter and a dedicated empty state. It is hard to argue SSHing into the home server is cheaper than pressing the button 20 times on a filtered list. Aggregation is the core and n does not come out — with cumulative failures at 20 to 40 across 15 domains, most rollup rows are count=1, and the one insight ("the same domain keeps 403ing") is visible by eyeballing 20 rows. The surface is wrong too — the daily loop is web/iOS, and diagnosis parked in a CLI does not get run. **✅ implemented 2026-07-30** (`Link.error` + `Link.retry_state`). Building it did sharpen the observation by one layer, though — `links.status='failed'` is only attached **after the attempts are spent** (`queue.Fail`), so a link lying down on backoff is still `pending` and **the progress rail is spinning** on screen. Which means the two things that need separating were not "awaiting failure vs confirmed failure" but **"working vs waiting"**.
  What follows is the original proposal.
  **The piece worth keeping**: put the reason for failure where the screen already stands. Add one field `error` to the `Link` schema (today it exists on `LinkDetail` only) so each row of a `status=failed` list prints the actual reason instead of "could not be collected". And one more on top — distinguish **"waiting to retry (run_after in the future)" from "attempts exhausted (attempts >= max)"** in a single word. Right now a link briefly lying down on backoff and a link that is dead forever look identical on screen, and **that is the one genuinely true observation this proposal found.** Bulk retry, dry-run and `-yes` all get cut.

### 4.5 Tagger signals

- **Wiring `author` into the tagger's input** — 08 §86 asked for it, but the premise has changed since. The YouTube adapter puts the whole `shortDescription` into `body_text`, so "videos have no body" is already false, and X/Twitter pushes author into title when title is empty, so author is already reaching the tagger. What is left is `meta[author]` = a person's name, nothing more. Worse, the measurement cannot see this effect — not one of the 123 golden items has an empty body_text, and the no-body figure that gets quoted is an ablation that stripped the body off articles. And the only case where an author lines up with the dictionary is a generic term like 「블로그」 or 「개발」, and `article` is golden's most frequent tag (53/123), so weighting it strongly **can fill top-3 with the most frequent tag and lift Recall@3 for entirely the wrong reason.** The number rises and the classifier gets worse — the kind of measurement most worth avoiding. **Resumption condition**: one 20-minute offline probe — fill author in for the 62 items of dev.jsonl only (test is not touched) and count "how many items have an author overlapping a dictionary alias", **excluding generic aliases.** **Under 10 and it ends there, no commit, no PR.** And the stretch this candidate really aimed at (links where the body was never captured) has no instrument — building the second set `nlu/golden/README.md` has already announced, as **30 real links with no body**, comes before author.
- **Nearby links (similarity recommendations)** — it has been measured that the similarity signal does not exist. All that goes into `link_terms` is matched dictionary surfaces, so the vocabulary is exactly the alias set of the 42 tags; across the 62 dev items the surfaces that actually fire number 158, and the top of that list reads data 0.34 · api 0.27 · tools/server/개발/go 0.23 in order. Pick any two development links and they share api, data and 개발 — "the IDF sum of shared surfaces" converges on "both of these are development posts". The IDF that would damp the collapse is not merely pinned at 1.0 below `minCorpusDocs`; forcing it on across the 62 items was not an improvement either (Recall@3 unchanged, and no-body fell dev 0.871→0.806 · test 0.820→0.803). **That is, at the corpus size this feature would ship into, the discriminating component is precisely switched off.** On top of that there is no golden for "similar", so there is no number to say whether it is good or bad. **The piece worth keeping**: the observation that the inspector's tag chips are `role="readonly"` + onRemove and nothing else, making it **a complete dead end with not one click leading to the next link**, is true. Make the chips links into the existing tag filter, and take **the tag with the smallest `link_count`** among them as the default jump target (`link_count` is already in the contract and the screen already receives it). Landing on `kubernetes` (7/62) instead of `article` (26/62) on dev golden cuts the flood down to 3 to 5 items, and that narrowing is a rule a human can understand, so even when it is wrong the cause can be named. **Re-discussion trigger: more than 300 links + even after the documents contributing to `link_terms` pass `minCorpusDocs`, "the narrowest tag" still pours out 40 or more** — at that point `corpus_df` has real skew in it and this becomes a measurable decision for the first time.

### 4.6 Web UI

- **Pinned searches (saved views)** — on the web they already exist. Filter, search, period and status are all in the URL as router search params, so **pressing Cmd+D makes the browser bookmark bar exactly that pin row.** Code 0 lines, tables 0, contract 0. For a new feature to beat that it would have to state what it does better than the bookmark bar, and there is nothing. "Sharing with iOS", the only argument for server-side storage, does not hold either — iOS has 2 tabs and the search screen is an explicitly listed cut candidate. A pin row permanently occupying the top of the list is exactly the same class of tax as the view switcher that got excluded (**the density toggle was released on iOS on 2026-07-29 and is therefore no longer part of that argument** — 10 §1.3). A stored query string nails contract parameter names into the DB, so under append-only migrations, changing a parameter once breaks the pins silently. **The piece worth keeping**: no table, no endpoint, no new pixels — **"restore the last view"**, which restores the last filter combination when you leave the list or search and come back. Storage is 1 web localStorage key / 1 iOS `@AppStorage`. A failed restore falls quietly through to empty filters, so a contract change does not break it. 20 lines on the web. **This settles for free whether 90% of the pain disappears with it** — evidence that "several" are needed only exists once I am clearing the restored combination and assembling a different one every single time.
- **A command palette (Cmd/Ctrl+K)** — of the proposed 3-source palette, two of the three are pure duplication. Navigation covers 5 screens and 4 of them are flat text links permanently visible in the top bar (there is no dropdown to route around in the first place). Recent link → inspector is the list screen itself, and J/K/Enter already do that job. **The piece worth keeping**: exactly one real friction remains — the tag filter bar is a single-line `overflow-x-auto` strip sorted by descending `link_count` with no truncation, so **the tags I use least are off the right edge of the screen with no route to them but horizontal scrolling.** So Cmd/Ctrl+K gets built **for tag jumping and nothing else**: 1 input + 1 list, one source (the tag cache), all 42 dictionary entries with no `link_count > 0` filter, case-insensitive substring matching (no fuzzy), Enter → apply the tag filter. No navigation entries, no recent links, no search inside the palette. What has to happen alongside: narrow the wording of the Cmd/Ctrl+K row in `shortcuts.ts` and the "palette" descriptions in 11 §1.2/§1.8/§9 and 10 §1.3 down to the actual behaviour (documents are the source, so documents first). **Promotion trigger for the navigation entries: when there are more than 6 screens, or the top bar actually overflows.**

## 5. What to look at first next

**This order is not "by value".** It is ascending cost-to-undo plus measurability. - If searches per week come out in single digits → **all of group B moves back**, and C1 is the only candidate left.
- If using the tag filter really does keep running into "have I already seen this?" → **C1 to number one.** This observation admits it depends on memory alone, because there is no instrument for it right now.
- If `removed` in `tag_feedback` passes 20 rows → 4.4's `feedback-golden` goes above anything on this list. Because that is not backlog, it is **an input to M5**.
