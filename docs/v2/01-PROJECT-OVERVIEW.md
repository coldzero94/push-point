# Push-Point - 프로젝트 개요

> Push-Point v2.1 — 마지막 업데이트: 2026-07-21

## 개요

Push-Point는 링크를 공유하면 자동으로 태그가 붙는 개인 링크 아카이브다. 유튜브 영상, 웹 아티클, 소셜 포스트를 iOS 공유 시트에서 한 탭으로 저장하면, 백그라운드에서 메타데이터·썸네일을 수집하고 통제된 태그 사전 기준으로 분류해 붙인다. 나중에 태그와 전문 검색으로 다시 찾는다.

단일 사용자 셀프호스트 앱이다. 서버는 Go 바이너리 하나(`pushpoint`)로 돌고, 데이터는 SQLite 파일 하나에 담기며, 외부 API 의존이 없다.

## v2 원칙

**인프라가 아니라 제품부터.** v1은 유저가 0명인 상태에서 Minikube + k8s + HPA, PostgreSQL, Redis, MinIO, OpenAI API까지 갖춘 설계였다. 오토스케일링은 유저가 생긴 뒤의 문제다. v2는 그 순서를 뒤집는다.

- 목표는 "내가 매일 쓰는 앱"이다. 완성의 기준은 배포 토폴로지가 아니라 실사용이다.
- 성능은 분산이 아니라 **단일 프로세스 설계의 질**로 확보한다. SQLite WAL, keyset 페이지네이션, 인프로세스 워커 풀 같은 설계 선택이 아래 성능 목표를 만족시킨다.
- v1의 k8s 매니페스트는 `deploy/k8s-future/`에 보존한다. Store/Queue/Tagger가 인터페이스 뒤에 있으므로, 유저가 생기면 구현체만 교체하면 된다. 지금 접는 것이지 버리는 것이 아니다.

## 핵심 기능

### 1. 저장

- 클라이언트는 **iOS 앱과 웹 앱 둘 다 대등한 full-feature 정식 클라이언트**다. 같은 `api/openapi.yaml` 계약을 소비하므로 저장·목록·검색·태그 필터·상세·태그 편집·삭제·재시도·통계를 양쪽에서 완결로 쓴다. **유일한 차이는 저장의 진입 방식**이다 — iOS 공유 시트 2초 진입은 OS 기능(Share Extension)이라 iOS 고유이고, 웹은 URL 입력창(+선택적 북마클릿)으로 저장한다. 호출하는 API와 결과는 동일하다.
- iOS Share Extension에서 한 탭으로 저장. 확장이 App Group의 공유 SQLite에 **직접 쓰고 태그·요약까지 그 자리에서 끝내므로**, 서버가 없어도 비행기 모드여도 저장이 완결된다. 실사용은 앱(M4)을 기다리지 않는다 — M2 종료부터 iOS 단축어로 매일 저장을 시작한다.
- 저장 API(`POST /api/v1/links`)는 동기 작업이 INSERT 두 번(링크 + 잡)뿐이라 p99 < 50ms로 즉시 응답한다. 스크랩·태깅·썸네일은 전부 비동기.
- 동일 URL 재저장은 `url_hash`로 감지해 중복 없이 기존 항목을 돌려준다.

### 2. 자동 태깅

- 자유 태그 "생성"이 아니라, 통제된 태그 사전(30~50개, 사용자 수정 가능)에 대한 **분류**로 문제를 좁힌다. LLM 없이 품질을 확보하는 유일한 길이다.
- 2단계 파이프라인: Phase A 규칙 기반(도메인 휴리스틱 + 조사 접미 정규화 기반 후보구 추출 + TF-IDF 스코어링·사전 매칭, 순수 Go) → Phase B ONNX 임베딩 분류(한국어 문장 임베딩, 코사인 유사도) 앙상블.
- v1의 OpenAI API 의존을 제거했다. 비용 0, 수백 ms 응답, 데이터가 외부로 나가지 않는다. 이 파이프라인이 프로젝트의 기술적 차별점이다.
- 태그 수동 수정은 `tag_feedback`으로 기록되어 Phase B 재랭킹 보정에 쓰인다.

### 3. 검색

- SQLite FTS5(trigram 토크나이저) 전문 검색. title / description / note / tags 대상, bm25 랭킹. 검색어 3자 미만이면 LIKE 폴백으로 동작한다 (400 거부 없음).
- 태그 필터, 기간 필터(`from`/`to`)와 조합 가능. 1만 링크 기준 30ms 미만 목표.

### 4. 개인 메모

- 링크마다 개인 메모(`note`)를 붙일 수 있고, 메모도 검색 대상에 포함된다.

## 사용자 시나리오

이 앱의 사용 단위는 하루에도 수십 번 반복되는 다음 루프다.

```
1. 유튜브/브라우저에서 관심 콘텐츠 발견
   ↓
2. 공유 시트 → Push-Point 한 탭 → 기기 안에서 저장·태깅 완료 후 시트 닫힘 (2초 미만, 서버가 없어도 성립)
   ↓
3. 서버가 백그라운드에서 스크랩 → 태깅 → 썸네일 (저장 후 3초 내 완료)
   ↓
4. 나중에 앱에서 태그 필터 또는 검색으로 재발견
   ↓
5. 다시 읽거나, 메모 추가, 태그 수정
```

핵심은 2번이다. 저장 마찰이 2초를 넘으면 매일 쓰는 앱이 못 된다. 그래서 저장 시점에는 아무것도 기다리지 않고, 나머지는 전부 잡 큐로 넘긴다.

## 개발 목표

성능 목표 (로컬 M-시리즈 기준, 매 마일스톤 검증 — p99 판정은 `just bench-http`, 마이크로벤치는 `just bench`):

| 지표 | 목표 |
|---|---|
| 저장 API p99 | < 50ms |
| 저장 → 태그 완료 (비동기) | < 3s |
| 검색 (FTS5, 1만 링크) | < 30ms |
| 링크 10만 건에서 목록 스크롤 API | < 50ms |
| 콜드 스타트 (바이너리 실행 → 서빙) | < 1s |

태깅 정확도 게이트: 실사용·임포트 링크에서 만든 golden set 100개(dev 50 / test 50, 스냅샷 기반 오프라인 평가)로 top-3 정확도를 `just eval`로 측정한다. 게이트는 **베이스라인 대비 상대 조건**이다 — M5 진입: Phase A가 "도메인 휴리스틱만" 베이스라인 대비 +15pp 이상, M5 종료: 앙상블이 Phase A 대비 +10pp 이상 (절대치 60% / 80%는 참고치). 측정 없는 "잘 되는 것 같다"는 금지.

## 차별점

- **비용 0**: 외부 API 호출도, 클라우드 인프라 비용도 없다. 내 머신에서 돈다.
- **프라이버시**: 저장한 링크·메모·태깅 과정 전부가 로컬에 머문다. 데이터가 외부로 나가지 않는다.
- **오프라인 동작하는 서버**: 태깅까지 포함해 인터넷 없이(스크랩 대상 접근 제외) 동작하는 단일 바이너리다.
- **측정으로 뒷받침하는 성능**: 위 표의 수치는 선언이 아니라 `just bench-http`·`just eval` 등 검증 커맨드가 매 마일스톤 확인하는 게이트다.

## 사용자

이 앱의 사용자는 나 하나다. v1은 큐레이터·연구자·개발자·디자이너를 타겟으로 잡았지만, 유저 0명인 제품의 페르소나 목록은 의미가 없다. v2의 유일한 성공 지표는 내가 매일 쓰는가이며, 모든 설계 결정(단일 사용자 인증, 별도 users 테이블 없는 스키마, 셀프호스트)이 여기서 나온다. 남에게 필요한 물건인지는 내가 4주 연속 매일 쓴 뒤에 판단한다.

## 명시적 비목표

v2에서 하지 않는 것:

- **k8s / HPA / 멀티 노드** — 유저가 생기면 `deploy/k8s-future/` 부활
- **회원가입 / 멀티유저** — 단일 사용자, 정적 API 키 하나로 인증
- **OpenAI 등 외부 LLM API 의존** — NLU 파이프라인이 이 프로젝트의 정체성
- **Android** — iOS 실사용 검증 후 판단
